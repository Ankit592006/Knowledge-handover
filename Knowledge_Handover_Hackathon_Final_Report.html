1. Executive Summary & Problem Statement

When a senior software engineer, architect, or technical lead departs a project or transitions between teams, organizations suffer severe tacit knowledge evaporation. Critical architectural rationale, undocumented operational workarounds, in-flight blockers, and cross-team dependencies are scattered across fragmented repositories: Architecture Decision Records (ADRs), pull requests, issue trackers, sprint notes, and commit logs.

Existing approaches to engineering handovers fail in four predictable ways:

  1. Manual Handover Checklists Are Incomplete & Stale: Outgoing engineers under transition deadline pressure write high-level summaries that omit edge-case workarounds (such as manual cache flushes before schema migrations) or reference deprecated API specifications.
  2. Generic LLM Summarizers Hallucinate & Hide Contradictions: Standard RAG/chat tools blend old and new documents into fluent prose. When a June specification says POST /v1/payments/charge and an October pull request replaces it with POST /v2/payment-intents, generic LLMs either guess or silently merge them—misleading the incoming successor.
  3. Unassigned Ownership & Missing Rationale Are Fabricated: Standard generative models fill gaps with plausible-sounding owners or deadlines rather than explicitly flagging that an issue has Assignee: UNASSIGNED or an undecided retry policy.
  4. Security, Secret Leakage & Clearance Violations: Raw commit notes and hotfix logs frequently contain live API keys, bearer tokens, or RESTRICTED vendor audit findings that must never be sent to external LLM APIs or exposed to unauthorized roles.
The Knowledge Handover Solution
Knowledge Handover transforms raw, fragmented engineering artifacts into an evidence-linked, contradiction-aware, human-approved 13-Section Continuation Plan. Every extracted claim is bound to a character-level citation (sourceId, body#chars:start-end, versionTag, sourceUpdatedAt), validated by a deterministic backend trust boundary (Layer L6), and locked behind a role-enforced Human Approval Gate before the incoming successor can access or acknowledge the handover package.

2. Core Architectural Differentiators (Why This Solution Wins)

1. Zero Silent Fabrication (Strict Provenance)

Every claim must link to at least one verified source excerpt. The L6 Deterministic Validation Layer checks every cited source_id against the database and strips any unauthorized or non-existent citation, automatically downgrading unsupported claims to unknown.

2. Contradiction & Staleness Surfacing

When sources disagree (e.g., issue-104 reports BLOCKED while notes-2026-10-15 reports IN PROGRESS), Agent 2 preserves both citations side-by-side with timestamps and labels the claim conflicting or potentially_outdated.

3. Never Invents Owners or Rationale

If an issue has no assignee or an ADR leaves a retry backoff parameter undecided, the platform preserves owner: null, attaches an explicit uncertainty flag, and auto-generates a targeted Clarification Question for the outgoing engineer.

4. Pre-LLM Secret Scrubbing & Prompt Guard

Before any artifact is chunked, stored, or sent to an LLM, regex redaction scrubs API keys, Bearer tokens, DB URLs, and private keys, while sanitize_untrusted_passage isolates adversarial prompt-injection strings.

5. AI Schema-Prohibited from Marking “Verified”

Pydantic validators on Agent 2 and the L6 backend gate strictly forbid AI from outputting status="verified". Only an authenticated human REVIEWER_SME or PROJECT_LEAD can transition a claim to verified.

6. Approval-Gated 13-Section Successor Plan

The Incoming Successor is blocked at the API level (HTTP 403) from viewing the Continuation Plan until human approval freezes an immutable HandoverVersion snapshot. Only the SUCCESSOR role can formally acknowledge receipt.

4. Deep Dive: LangGraph 3-Agent Pipeline & Dual-Mode LLM Adapter

The AI reconstruction engine (app/agents/) uses a LangGraph StateGraph state machine with conditional stop-on-failure edges (node_knowledge_extraction $\rightarrow$ node_evidence_verification $\rightarrow$ node_risk_dependency). If any agent fails after bounded retries (LLM_MAX_RETRIES=2), orchestration halts immediately and returns HTTP 503 rather than publishing a partial or corrupted handover draft.

4.1 The Three Specialized Agents

  • Agent 1 — Knowledge Extraction Agent (app/agents/knowledge_extraction/agent.py): Wraps every retrieved passage in <untrusted_evidence source_id='...'> tags after running sanitize_untrusted_passage() to neutralize prompt-injection attempts. Extracts structured CandidateClaimSchema items across 8 types (project_overview, technical_context, key_decision, completed_work, active_work, blocked_work, responsibility, operational_info) and generates UnresolvedQuestionSchema clarifications whenever rationale, runbooks, or owners are missing.
  • Agent 2 — Evidence Verification Agent (app/agents/evidence_verification/agent.py): Cross-examines every candidate claim against the full set of scoped passages and their source_updated_at timestamps. Detects status contradictions (producing ConflictRecordSchema with both excerpts and timestamps), identifies superseded documentation (marking claims potentially_outdated), and enforces a Pydantic @field_validator that raises a ValueError if an LLM ever attempts to output evidence_status="verified".
  • Agent 3 — Risk & Dependency Analysis Agent (app/agents/risk_dependency/agent.py): Synthesizes explicit project blocker, risk, and dependency records (distinguishing source_supported vs. inferred) and generates a priority-ranked list of actionable onboarding steps (CandidateNextActionSchema) linked directly to claim codes.

4.2 Dual-Mode OpenAI-Compatible (Groq) + Deterministic Extractive Adapter

In app/agents/adapter/llm_adapter.py, invoke_structured_model() supports three runtime providers configured via LLM_PROVIDER:

  1. Cloud OpenAI-Compatible Inference (LLM_PROVIDER="openai_compatible" — Production Default on Render): Invokes Groq’s high-speed inference endpoint (https://api.groq.com/openai/v1/chat/completions) with llama-3.3-70b-versatile at temperature=0.0, injecting the exact Pydantic JSON Schema into the system prompt and validating the response via response_schema.model_validate_json().
  2. Local Ollama Inference (LLM_PROVIDER="ollama"): Connects to local http://localhost:11434/api/chat with qwen2.5:7b-instruct in JSON mode.
  3. Transparent Deterministic Fallback (deterministic_extractive / rule-grounded-extractor-v1): If the cloud LLM is unreachable, rate-limited, or unconfigured in CI tests, the adapter seamlessly executes a deterministic, rule-grounded extractor and records the exact provider, latency (ms), and fallback reason in agentTelemetry.
